**As a** .NET host developer,
**I want to** plug my own persistence behind granular, account-scoped store interfaces from day one,
**so that** my session data lives in my own database choice and the SDK never imposes one.

end-to-end in the in-memory reference store, one real write-then-read flowing through the async
factory, and the contract-kit pattern proven with the first contract class passing against the
reference implementation. It is the tracer slice every later plan expands from.

Purpose: prove the seam architecture (interface → factory → account-scoped instance → typed
record → contract suite) before expanding to all five stores.
Output: building solution, one store seam wired end-to-end, first contract class green,
SKELETON.md decisions made real.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Host code → SDK store seam | Host-supplied AccountId strings and record payloads cross into SDK-owned validation and storage structures |
| SDK → ILogger output | Exception/log messages could carry host-supplied values (account IDs, record fields) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Information Disclosure | AccountId / store values in exception messages and ILogger calls | high | mitigate | SdkException subtypes carry no payload field values in messages — messages name the validation rule violated or the operation, never embed record contents; acceptance criteria in plan 01-04's error-surfacing task enforce message discipline (ASVS V7.1) |
| T-01-02 | Information Disclosure | Cross-account data bleed through shared static state in the in-memory reference store | high | mitigate | No global mutable statics (Pitfall 8 hard rule): all state lives under factory instance keyed (Capability, AccountId); the Two_accounts_isolated_same_address contract test in Task 1 is the enforcement test; parallel isolation rule family lands in plan 01-03 |
| T-01-03 | Tampering | default(AccountId) or unvalidated strings reaching store namespaces and host persistence keys | medium | mitigate | AccountId construction is validation-only (private ctor + Create validation), making default struct misuse detectable; acceptance criteria include ordinal-casing distinctness; documented A4 rule is additive-safe |
| T-01-04 | Repudiation | In-memory store implying durability it does not have (host believes data persisted) | low | accept | D-09 mandates honest documentation: README/docs state the reference store does not survive restart; reference-impl positioning is prototype-capable, deliberately documented — accepted because the contract surfaces it in docs the host reads before choosing the impl |
</threat_model>
