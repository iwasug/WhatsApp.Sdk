<objective>
**As a** .NET host developer,
**I want to** register, observe, and remove many WhatsApp accounts in one process through a single manager that never shares an account's internals,
**so that** concurrent accounts scale up and down at runtime without a rebuild or a restart.

Purpose: Phase 1's `StoreRegistry` already proved atomic registration and snapshot disposal for stores; this plan lifts the same discipline to whole account graphs, proving the multi-account shape before any hosting abstraction lands.
Output: composition-ready `IWhatsAppSessionManager`, `AccountRuntime`, `DefaultAccountRuntimeFactory`, plus the first account lifecycle test.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Host request -> SessionManager | Untrusted AccountId and descriptor strings cross into registration; manager validates before any store/socket work |
| Manager -> per-account store/socket | Runtime graph constructed from host-provided factories and options; isolation failure here leaks across accounts |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-01 | Information Disclosure | Cross-account store read (one account resolving another account's StoreSession) | critical | mitigate | AccountRuntime StoreSession is resolved once through StoreRegistry.CreateSessionAsync keyed by its own AccountId; no manager state surface accepts an AccountId that is not the registered one; covered by the Wave-2 isolation suite before close |
| T-07-02 | Information Disclosure | Global static mutable state leaking per-account data across accounts | high | mitigate | All registry state fields are instance fields behind _lifecycleGate; AccountRuntime graph is entirely per-instance; plan 07-02 adds a reflection audit that fails the build on any non-readonly static field of mutable types |
| T-07-SC | Tampering | npm/pip/cargo installs (the 10.0.12 ME abstractions) | high | mitigate | Package-legitimacy gate in the research: all three packages are OK from nuget.org flatcontainer; package installs are the three PackageVersion entries added here under T-07-SC and never auto-approved |
</threat_model>
